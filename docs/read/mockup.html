docs/read — 設計案

栞

読むための画面と、読んだ記録を1つにした個人用 PWA。青空文庫はアプリ内から落として縦組みで読む。Markdown のノートも同じ画面で読み返せる。ミュージック・DESK と同じ作り（ビルド不要の素の ES モジュール／GitHub Pages／IndexedDB／オフライン）に乗せる前提。

1管理アプリと読書アプリを分けない。1アプリ・2モード。記録が発生するのは「読み終わった瞬間」「線を引いた瞬間」であって、後から別アプリを開いて入力する習慣は続かない。分けた時点で記録は埋まらなくなる。
2ただし作る順番は管理が先。ビューアは DRM フリーの EPUB / PDF / テキストしか開けない。Kindle と紙の本は技術的に開けない。蔵書の大半がそちらなら、ビューアを先に作っても使う場面が無い。
3中心機能は抜き書き。読了数や星の数は自分用には情報量がほぼゼロ。後で参照されるのは引用と、そのとき何を思ったかだけ。ここを一等地に置く。
縦組み・雰囲気5種・紙の調整・タップ送りを実装済み。端末の全画面で開く

02

タブレット — 本文とノートを同時に開く

タブレットで縦持ち・1段組にするとスマホの拡大版にしかならない。横持ちの価値は「本文を読みながら右に書ける」ことにある。選択した文はそのまま右に落ち、本文側には薄い印が残る。研究読みはこの形が要る。

紙の本を読むとき、指は次のページの端をさわっている。残りがどれだけあるかを、数えずに知っている。画面にはこれが無い。だから残量は数字で補うしかないのだが、ページ数は補いになっていない。読む速さを知らない数字だからだ。実測すればいい。一行に何秒かかったかは、ページを送った間隔からわかる。十ページも読めばその人の速さは出る。あとは残りの字数を割ればいい。「あと四十二ページ」より「あと十八分」のほうが、寝る前に読み続けるかどうかを決められる。

03

本をどこから入れるか

ここは形式ごとに事情がまったく違う。まとめて「対応」とは書けないので、一つずつ分ける。

形式入れ方アプリ内で完結するか
青空文庫アプリ内で作者・題名を検索して、そのままダウンロードする見込み
Markdown / テキストファイル選択、または共有シートからする
EPUB（DRM フリー）ファイル選択、または共有シートからする
洋書（Gutenberg 等）ブラウザで落としてから、共有シートで栞に渡す半分だけ（検索はアプリ内、取得は外）
PDF（自炊）ファイル選択する（タブレットのみ）
Kindle入れられない。棚に登録して進捗を手で動かすだけしない
青空文庫
本家 www.aozora.gr.jp は CORS ヘッダが無いのでブラウザから直接は読めない。GitHub のミラー（aozorabunko.github.io）なら GitHub Pages 配信なので CORS が通る見込みで、ここを叩く設計にする。作品一覧の CSV を初回に一度だけ取り込んで端末内に索引を作れば、以後の検索はオフラインで済む（約2万作品）。本文はテキスト版ではなく XHTML 版を使う — ルビが <ruby> タグで入っているので縦組みにそのまま流せる。テキスト版は Shift_JIS ＋ 《》［＃］ の独自注記で、パーサを1本書くことになる。着手前に1作品 fetch して実際に通るか確かめること。ここが通らなければこの機能は成立しない
洋書
期待しないほうがいい。gutenberg.org は自動取得を制限していて、CORS も期待できない。Gutendex のような API で検索と書誌は取れても、本文ファイルの実体は gutenberg.org 側にあるので別問題になる。現実的な形は、アプリ内で探して端末のブラウザに渡し、落ちてきたファイルを共有シートから栞に投げ返す（Web Share Target を manifest に書く。Android では効く、iOS は非対応なのでファイル選択で拾う）。自前の CORS プロキシを1枚立てれば完結するが、サーバーを持たない原則を壊すので最後の手段
Markdown
パーサは自前で足りる（見出し・箇条書き・引用・強調・コード・罫線・リンク）。ライブラリは要らない。ただし縦組みにはしない。箇条書きとコードと表が縦に流れると、どこを見ればいいかわからなくなる。横組み固定にする。抜き書きの書き出しと同じ形式なので、書き出しと取り込みが対称になる — ThinkOS 側のノートをそのまま読み返せる
04

雰囲気 — 配色ではなく組み方ごと変える

和書と洋書で変えるべきなのは色ではない。行の長さ、字送り、段落の頭、書体の系統が全部違う。配色だけ切り替えても洋書は洋書に見えない。だから「雰囲気」は組版のプリセットとして持つ。

雰囲気組み方・書体紙効くもの
和・縦縦組み／明朝／行間ゆったり／ルビあり生成り青空文庫の小説、日本語の EPUB
覚え書き横組み／ゴシック／行間つめ白磁Markdown、実用書、自分のノート
洋・古典横組み／欧文セリフ／ハイフネーション／段落一字下げ／頭文字を大きく古紙洋書
研究横組み／ゴシック／小さめ／余白を削る白磁通読ではなく参照。ノート併置
夜直前の組み方を保つ／紙だけ墨に墨暗所。紙の目は弱めに落ちる

雰囲気を選ぶと下の項目（紙・書体・文字・行間・版面）がまとめて動く。動いたあとで個別に触れる。プリセットは出発点であって、固定ではない。

05

紙に寄せる — どこまで効いて、どこから邪魔になるか

画面は発光しているので、紙にはならない。できるのは「発光している感じを減らす」ところまでで、それ以上やるとコントラストが落ちて読みにくいだけになる。調整できるものと、上限を決めておく。

項目中身実装
紙の色白磁／生成り／古紙／セピア／墨。純白は目が疲れる。既定は生成りtoken を差し替えるだけ
紙の目なし／弱／中／強。ざらつきを1枚重ねる。ここがいちばん効くSVG の feTurbulence を data URI で1枚。画像を読み込まないので軽い
綴じ側の陰り本を開いたときノドが少し暗くなる、あれ。縦組みなら右、横組みなら左グラデーション1枚
版面広く読む／標準／余白を取る。紙の本は余白が広いが、スマホで真似ると読める量が減る余白の変数1つ
インクの濃さ本文を純黒（#000）にしない。紙側とセットで決める紙の token に同梱
上限を抑える
紙の目を強くすると、文字と地のコントラストが縮むだけで読みやすさは上がらない。効くのは、効いていると気づかない強さまで。「強」でもまだ控えめな位置に上限を置く
夜だけ別扱い
墨の紙にノイズを載せると、画面が真っ黒でなくなるので OLED の省電力が消える。夜の既定は「弱」にして、そこは自覚的に払う
描き直さない
ノイズは背景に固定し、ページ送りでは動かさない。送るたびに再描画すると電池を削る。めくりアニメを既定オフにしている理由と同じ
06

入れる機能・入れない機能

「読書体験を楽しむ」で普通に挙がるものの大半は、自分ひとりで使うアプリでは効かない。判断を先に書く。

機能判断理由
縦組み入れる日本語の小説では体験差がいちばん大きい。writing-mode:vertical-rl で実装可能（上のデモが実物）。ただし横組みとページ送りの計算が別物になるので、実装コストは相応にある
残り時間の実測入れる実測の分/ページから「この章あと◯分」。ページ数より行動を決められる。DESK の予定にも流せる
抜き書きの再会入れる1日1枚、過去の抜き書きを出す。研究用途では復習が効く。枚数を増やすと見なくなるので1枚固定
読了時の1問入れる星をつけさせる代わりに「一番残った文は」を抜き書きから1つ選ばせる。読了記録が引用に繋がり、後から使える形で残る
読書の記録入れるいつ・何分読んだかを DESK の集中セッションと同じ形で残す。冊数ではなく時間で見る
Markdown を読む入れる自前パーサで足りる。ThinkOS のノートを読書と同じ画面で読み返せる。ただし横組み固定
青空文庫の取り込み入れるアプリ内で検索して落とせる。縦組みとルビを実装する主目的でもある（第3章）
雰囲気のプリセット入れる組版ごと切り替える。和書と洋書で変えるべきは色ではない（第4章）
紙の目・紙の色入れるSVG ノイズ1枚。ただし上限は控えめに抑える（第5章）
ページめくりアニメ既定オフ紙をめくる演出は最初の3日で邪魔になる。60fps 維持のコストと電池も払う。設定で「なし / 薄いフェード」のみ
星評価・点数入れない他人に見せないなら★4と★5の区別に意味がない。付けるのが面倒になって記録自体が止まる
連続日数・バッジ入れない途切れた日に開かなくなる。読書は音読やゲームと違い、1日空けるのが普通
効果音・BGM入れない音はミュージック側の担当。両方から音を出すと事故る
積読の総数表示入れない数えると買わなくなる方向にしか働かない。今月の出入り（＋2 / −1）だけ出す
07

正直なところ（先に潰しておく制約）

Kindle
開けない。回避策も無い。DRM があり、Web から読む手段は提供されていない。Kindle の本は「棚に登録して進捗を手で動かす・抜き書きは手打ちかカメラ」までしかできない。蔵書の大半が Kindle なら、ビューアを作る意味はほぼ無い。ここが設計全体の分岐点なので、作り始める前に自分の蔵書の内訳を数えたほうがいい
EPUB
DRM フリーなら開ける。EPUB は zip + XHTML なので、ブラウザ標準の DecompressionStream('deflate-raw') で展開できる。epub.js のような外部ライブラリを抱えずに、ミュージックや DESK と同じ「素の ES モジュール」のまま実装できる
PDF
自炊 PDF は描画に pdf.js が要る（数 MB を同梱する形になる）。しかもスキャンした固定レイアウトは文字サイズを変えられないので、スマホでは実用に耐えない。タブレット専用と割り切るのが正しい
iPhone / iPad
ホーム画面への追加は Safari 限定。保存領域は長期間開かないと OS に消されうる（ミュージックと同じ話で、persist() は打っておく）。本の実体を端末に持つ以上、容量の確認表示は必須
同期
ミュージック・DESK と同じく端末内のみ。ただし読書は「スマホで読んで、タブレットで続きから」が起きるので、進捗だけは端末をまたぎたくなる。JSON の書き出し／読み込みでは足りない。Google ドライブの appDataFolder に進捗と抜き書きだけを置く方式（本体は各端末）が現実的な落としどころ
08

作る順番

各段階で単体で使えるようにする。v0.1 だけで止めても損にならない構成にしてある。

版中身これだけで使えるか
v0.1棚 ＋ 手動の進捗 ＋ 抜き書き（手打ち・カメラ OCR）＋ 読書の記録使える。紙でも Kindle でも成立する。ビューアが無くても困らない
v0.2Markdown / テキストのビューア（横組み・雰囲気・紙の調整）いちばん安い。手元のノートがすぐ読める。ここで表示まわりを全部作り切る
v0.3EPUB ビューア（横組み・タップ送り）DRM フリーの蔵書がある場合のみ効く
v0.4縦組み ＋ ルビ ＋ 青空文庫の取り込み。選択からの抜き書き、タブレットの分割表示まとめて1段。青空文庫は縦組みとルビが揃って初めて意味がある
v0.5洋書の取り込み（共有シート）、DESK / ConTodo 連携、ドライブ同期、PDF周辺。無くても本体は回る
09

既存アプリとの接続

見た目
ミュージックのテーマ体系（墨／霧／灰／藍鉄／生成り／白磁 ＋ アクセント ＋ フォント）をそのまま流用する。読書アプリ側で足すのは本文の設定だけ ― 文字サイズ・行間・字送り・余白・縦横組み
DESK
同一オリジンなので localStorage を共有できる。今日の読書分数を DESK の集中セッション（kind: read）に書く。DESK 側は何も変えずに時間が積算される
ConTodo
「◯◯を30分読む」をタスクとして受け取り、読み終わったら消化を返す
ThinkOS
抜き書きを Markdown で書き出す。引用・出典・自分の反応・タグの4点セットで出せば、そのまま文献ノートとして使える
