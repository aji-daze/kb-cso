栞

読むための画面と、読んだ記録を1つにした個人用 PWA。ミュージック・DESK と同じ作り（ビルド不要の素の ES モジュール／GitHub Pages／IndexedDB／オフライン）に乗せる前提。

1管理アプリと読書アプリを分けない。1アプリ・2モード。記録が発生するのは「読み終わった瞬間」「線を引いた瞬間」であって、後から別アプリを開いて入力する習慣は続かない。分けた時点で記録は埋まらなくなる。
2ただし作る順番は管理が先。ビューアは DRM フリーの EPUB / PDF / テキストしか開けない。Kindle と紙の本は技術的に開けない。蔵書の大半がそちらなら、ビューアを先に作っても使う場面が無い。
3中心機能は抜き書き。読了数や星の数は自分用には情報量がほぼゼロ。後で参照されるのは引用と、そのとき何を思ったかだけ。ここを一等地に置く。
縦組み・タップ送り・文字設定を実装済み。端末の全画面で開く

02

タブレット — 本文とノートを同時に開く

タブレットで縦持ち・1段組にするとスマホの拡大版にしかならない。横持ちの価値は「本文を読みながら右に書ける」ことにある。選択した文はそのまま右に落ち、本文側には薄い印が残る。研究読みはこの形が要る。

存在への問いは、今日では忘れられている。とはいえ、この問いが忘れられているということ自体は、けっして自明の事柄ではない。むしろ問いが忘却されえたという事実のうちに、問いそのものの性格が現れている。問いを立てるということ自体が、問うている当のものの存在様式にすでに属している。われわれは、存在とは何かをあらかじめ何ほどか了解しているからこそ、存在を問うことができる。この了解は漠然としており、概念の形をとっていない。しかしそれが皆無であるなら、問いを発することすらできないはずである。したがって存在への問いは、外から持ちこまれるものではなく、現存在そのものの構造から立ちあがってくる。

03

入れる機能・入れない機能

「読書体験を楽しむ」で普通に挙がるものの大半は、自分ひとりで使うアプリでは効かない。判断を先に書く。

機能判断理由
縦組み入れる日本語の小説では体験差がいちばん大きい。writing-mode:vertical-rl で実装可能（上のデモが実物）。ただし横組みとページ送りの計算が別物になるので、実装コストは相応にある
残り時間の実測入れる実測の分/ページから「この章あと◯分」。ページ数より行動を決められる。DESK の予定にも流せる
抜き書きの再会入れる1日1枚、過去の抜き書きを出す。研究用途では復習が効く。枚数を増やすと見なくなるので1枚固定
読了時の1問入れる星をつけさせる代わりに「一番残った文は」を抜き書きから1つ選ばせる。読了記録が引用に繋がり、後から使える形で残る
読書の記録入れるいつ・何分読んだかを DESK の集中セッションと同じ形で残す。冊数ではなく時間で見る
ページめくりアニメ既定オフ紙をめくる演出は最初の3日で邪魔になる。60fps 維持のコストと電池も払う。設定で「なし / 薄いフェード」のみ
星評価・点数入れない他人に見せないなら★4と★5の区別に意味がない。付けるのが面倒になって記録自体が止まる
連続日数・バッジ入れない途切れた日に開かなくなる。読書は音読やゲームと違い、1日空けるのが普通
効果音・BGM入れない音はミュージック側の担当。両方から音を出すと事故る
積読の総数表示入れない数えると買わなくなる方向にしか働かない。今月の出入り（＋2 / −1）だけ出す
04

正直なところ（先に潰しておく制約）

Kindle
開けない。回避策も無い。DRM があり、Web から読む手段は提供されていない。Kindle の本は「棚に登録して進捗を手で動かす・抜き書きは手打ちかカメラ」までしかできない。蔵書の大半が Kindle なら、ビューアを作る意味はほぼ無い。ここが設計全体の分岐点なので、作り始める前に自分の蔵書の内訳を数えたほうがいい
EPUB
DRM フリーなら開ける。EPUB は zip + XHTML なので、ブラウザ標準の DecompressionStream('deflate-raw') で展開できる。epub.js のような外部ライブラリを抱えずに、ミュージックや DESK と同じ「素の ES モジュール」のまま実装できる
PDF
自炊 PDF は描画に pdf.js が要る（数 MB を同梱する形になる）。しかもスキャンした固定レイアウトは文字サイズを変えられないので、スマホでは実用に耐えない。タブレット専用と割り切るのが正しい
iPhone / iPad
ホーム画面への追加は Safari 限定。保存領域は長期間開かないと OS に消されうる（ミュージックと同じ話で、persist() は打っておく）。本の実体を端末に持つ以上、容量の確認表示は必須
同期
ミュージック・DESK と同じく端末内のみ。ただし読書は「スマホで読んで、タブレットで続きから」が起きるので、進捗だけは端末をまたぎたくなる。JSON の書き出し／読み込みでは足りない。Google ドライブの appDataFolder に進捗と抜き書きだけを置く方式（本体は各端末）が現実的な落としどころ
05

作る順番

各段階で単体で使えるようにする。v0.1 だけで止めても損にならない構成にしてある。

版中身これだけで使えるか
v0.1棚 ＋ 手動の進捗 ＋ 抜き書き（手打ち・カメラ OCR）＋ 読書の記録使える。紙でも Kindle でも成立する。ビューアが無くても困らない
v0.2EPUB ビューア（横組み・タップ送り・文字設定）DRM フリーの蔵書がある場合のみ効く
v0.3縦組み ＋ 選択からの抜き書き ＋ タブレットの分割表示ここで「読書体験」の側が完成する
v0.4DESK / ConTodo 連携、ドライブ同期、PDF周辺。無くても本体は回る
06

既存アプリとの接続

見た目
ミュージックのテーマ体系（墨／霧／灰／藍鉄／生成り／白磁 ＋ アクセント ＋ フォント）をそのまま流用する。読書アプリ側で足すのは本文の設定だけ ― 文字サイズ・行間・字送り・余白・縦横組み
DESK
同一オリジンなので localStorage を共有できる。今日の読書分数を DESK の集中セッション（kind: read）に書く。DESK 側は何も変えずに時間が積算される
ConTodo
「◯◯を30分読む」をタスクとして受け取り、読み終わったら消化を返す
ThinkOS
抜き書きを Markdown で書き出す。引用・出典・自分の反応・タグの4点セットで出せば、そのまま文献ノートとして使える
07

保存するもの

ストア中身
books書誌（題・著者・形式＝紙/Kindle/EPUB/PDF・状態・入手日・読了日）
filesEPUB / PDF の実体（Blob。キーは本 ID）
marks進捗（CFI 相当の位置／ページ番号／%）と、前回止まった位置
notes抜き書き（引用・位置・自分の反応・タグ・日時）
sessions読書セッション（本 ID・開始・分数・進んだ量）
settingsテーマ・本文設定・最後に開いていた本

ミュージックの tracks / blobs / art / playlists / settings と同じ分け方。実体（files）だけ別ストアにしておくと、本を消さずに実体だけ捨てて容量を空ける、ができる。
